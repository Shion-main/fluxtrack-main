## Result in one paragraph

The automated suite is green and the app does not crash in normal use, but
**FluxTrack can still record wrong attendance**. Every High finding below was
reproduced against real SQL Server through the real views, and none is caught by
the 1,419 existing tests. Most share one pattern: a rule was built for the common
path, and a second path (cancelled classes, merged sections, a forgotten checkout,
an IFO edit) does not follow it. Findings from the 30 September audit are not
repeated here.

## High — wrong attendance or schedule records

### H1. Cancelled classes still count against attendance

`scheduling/reporting.py:511`, `:551`, `:676` use `scheduled=Count("id")`, which
includes CANCELLED sessions. **Reproduced:** one held class plus one cancelled class
reports `scheduled=2, held=1, 50%` where the correct figure is 100%. A typhoon
suspension therefore lowers every affected faculty member's percentage on Dean
reports, the IFO dashboard, scorecards and weekly reports. This violates SRS IFO-12
("reporting shall exclude those sessions") and the `SessionStatus.CANCELLED` comment.
Classes later today, not yet started, are counted the same way, so percentages also
read low during the day (from the code, not separately reproduced).

### H2. A forgotten checkout can never be closed

Nothing moves an ACTIVE session to COMPLETED except the faculty member on the same
day, a force handover in that room, or an online checkout. The sweep only handles
SCHEDULED. **Reproduced:** the next day the session is still `active`, `actual_end`
is empty, the faculty re-scan returns `no-schedule`, and `close_term` is blocked by
`active_sessions` (`scheduling/term_lifecycle.py:180`). IFO has no screen to resolve
it, so one forgotten checkout can stop a term being closed.

### H3. A forgotten checkout turns the next class Absent

`scheduling/resolver.py:75-82` treats any ACTIVE session as the current one without
checking that it has ended. **Reproduced:** a class ending 09:30 left open, then a scan
of the next class's room at 09:35, returns `wrong-room` for the *old* class. Confirming
moves the finished class into the new room, and the sweep marks the class actually
being taught `absent`.

### H4. Lifting a suspension marks classes Absent

`scheduling/suspensions.py:132` returns cancelled sessions to SCHEDULED with no check
that their time has passed. **Reproduced:** suspend at 06:00, lift at 12:00, and the
sweep marks all 3 of the morning's classes `absent`, though faculty were told not to
come. This is the mass false-Absent the suspension feature exists to prevent.

### H5. A room change splits merged sections and marks one Absent

`web/scan.py:192-200` moves only the scanned section, while same-room merging depends
on matching `room_id` (`scheduling/merge.py:74`). **Reproduced:** two merged sections
with different course codes; the faculty member confirms a move and checks in. The
anchor is `active`, the sibling stays in the old room, and the sweep marks it `absent`.

### H6. Any class edit undoes a Dean-approved move and can double-book

`update_schedule` (`scheduling/schedule_ops.py:259`) rewrites room and time on all
future sessions, but the conflict check at `:234` only runs if those fields changed.
**Reproduced:** a Dean approval moved a session to room B because room A was taken.
IFO changed only the enrolment count; the session returned to room A in the same slot
as the other class, with no warning.

### H7. Online sessions stop getting a checker

`assign_online` has no scheduler job (`scheduling/management/commands/runscheduler.py:108`
registers `materialize`, `sweep`, `weekly_report`, `push_outbox`, `maintenance`) and no
systemd timer. **Reproduced:** with a standing online checker on duty, newly materialized
online sessions have `online_checker = None`. Assignment only happens when IFO saves a
new online posting (covering 14 days) or someone runs the command by hand, so checkers'
lists run dry after about two weeks.

### H8. Adding a holiday does not affect classes already created

`web/ifo.py:2220` only inserts the break; unlike a suspension it does not cancel
existing sessions, which are materialized ahead of time. **Reproduced:** on the holiday
a faculty scan still returned `checked-in`; an unscanned session stays `scheduled`
indefinitely; if IFO later deletes the holiday the sweep marks it `absent`.

## Low

- **Offline replay:** a malformed timestamp returns 500 and rolls back the whole batch
  (`web/checker.py:580`). Reproduced, but the shipped client always sends valid values.
- **Offline precache:** `web/views.py:192` precaches the unhashed script, while production
  pages load the hashed name, so the offline page depends on an earlier controlled visit
  having cached it. In development the `?v=` URL fails the worker's filter entirely.
  From the code only; **not tested in a real browser.**
- **Global lock timeout:** creating 4,000 sessions took 13.9 s on LocalDB, longer than the
  10 s lock timeout (`ops/locking.py:22`), so writes during term activation could fail.
  Timing measured; the failure itself was not reproduced under real concurrency.
- **Dropped classes vanish from reports:** `scheduling/reporting.py:400` excludes archived
  schedules, so a dropped class's earlier held and absent records leave Dean and IFO
  reports but stay in HR exports. Documented as assumption A5; worth a decision.
