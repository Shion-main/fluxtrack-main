## Assessment

FluxTrack is a substantial institutional attendance and facility-management application. Its architecture is appropriate for its users: a Django monolith, SQL Server, server-rendered role-specific pages, htmx, and a small PWA layer. Core policy decisions are often isolated into pure functions, and its regression suite covers a broad range of institutional workflows.

I would require the high-priority issues below to be addressed before relying on the system as an official production attendance record. The principal gaps concern account isolation in browser storage, attendance state transitions, room allocation concurrency, and resource limits. Passing existing tests does not establish those missing guarantees.

This audit reviews the current checkout, not only a branch diff. Application code was left unchanged. Findings are source-verified unless explicitly marked otherwise; concurrent interleavings, browser cache behavior, and external deployment were not reproduced end to end. No destructive resource-exhaustion or outbound-network probes were run.

## Understanding of the system

The users are MMCM faculty, checkers, guards, IFO administrators, deans, HR administrators, and system administrators. Faculty start/end classes and request modality changes; checkers verify physical or online attendance; deans approve shifts; IFO manages academic terms, imports, schedules, room inventories, bookings, suspensions, and corrections; HR and deans consume scoped attendance reports; guards monitor room occupancy.

| Component | Responsibility |
|---|---|
| `accounts` | Seven-role identity model, departments, Entra PKCE authentication, provisioning rules, profile photographs |
| `campus` | Buildings, floors, rooms, QR/manual resolver credentials, room service state |
| `scheduling` | Recurring schedules, dated sessions, attendance policy, modality requests, imports, terms, jobs, reporting |
| `verification` | Checker assignments, decision functions, validation records, durable offline replay receipts |
| `ops` | Availability, bookings, notifications/push, audit records, report files, shared cache, job observability |
| `web` | Authenticated HTML/htmx/JSON surfaces and role/ownership checks |
| `config` / `deploy` | Environment configuration, SQL Server, WSGI, liveness, Nginx/Gunicorn/systemd deployment |

The important data distinction is recurring `Schedule` versus dated `Session`. Attendance status and timestamps belong to sessions; future sessions are materialized by the dedicated scheduler. Approved shifts affect both existing sessions and future materialization. Merged sections share attendance propagation while retaining separate records. Reports derive from those records rather than browser state.

Production is intended to use one EC2 host, private RDS SQL Server, private media storage, multiple web workers, and one APScheduler process. That is a pragmatic initial topology; live Entra/AWS cutover and restore rehearsal remain external verification obligations documented by the project.

## Strengths verified in source

- Genuine PKCE backend and a provisioning pipeline that rejects unknown or inactive institutional accounts.
- Explicit role decorators and ownership/department scoping across the main surfaces, including refusal for deans without a department.
- Pure faculty/checker resolvers and shared predicates for no-show policy, duty scope, and effective modality.
- Signed faculty confirmation tokens bound to the user, with expiry, current-state re-resolution, and nonce protection.
- Durable checker replay receipts, avoiding reliance solely on a short-lived cache for offline deduplication.
- Atomic merge propagation and faculty/term scoping that preserve co-scheduled section consistency.
- Status-guarded no-show updates, transactional term activation/materialization, and a database-enforced single-active-term invariant.
- Shared break/suspension logic; protected foreign keys and explicit room/building deletion blockers.
- Deliberate SQL Server handling, including queryset materialization before follow-up writes and attention to parameter limits.
- Photo byte/pixel limits, re-encoding and metadata removal, plus authenticated photo delivery.
- CSV formula-injection defenses, scoped reports, and aggregate code that avoids count inflation from multiple joins.
- Production startup rejects weak secrets, DEBUG, wildcard hosts, invalid OAuth callback hosts, and insecure database certificate settings.
- Same-origin vendored frontend dependencies, CSRF middleware, private HTML cache headers, scheduler monitoring, retention, and a recovery runbook.

These controls are valuable, but some are bypassed by alternate paths described below.

## Findings

Priority: **High** should be resolved before production attendance use; **Medium** should be resolved in the hardening release. Priorities reflect this product's system-of-record purpose, not a formal CVSS assessment.

### 1. High — service worker stores authenticated responses across accounts

**Source:** `web/views.py:205–227`; logout at `web/views.py:120`.

The branch described as static caching actually accepts every successful same-origin GET outside navigation. This includes fetched notification content, profile images, and authenticated htmx partials. It neither allowlists public assets nor honors private/no-store response directives. Origin-wide CacheStorage survives logout, and a network failure can replay a previous user's cached response after an account change. The HTML middleware's no-store header does not prevent explicit Cache API writes.

**Fix:** cache only an explicit public asset allowlist; bump the worker cache version to remove legacy sensitive entries. Add shared-device browser regression checks for logout, account switch, and offline requests.

### 2. High — public icon endpoint permits unbounded image allocation

**Source:** `web/urls.py:202`; `web/views.py:289–306`.

The anonymous `icon-<int:size>.png` route passes an unrestricted integer to Pillow resize and fallback image allocation. Memory demand grows quadratically. An oversized request can exhaust a worker; catching an exception and allocating the same dimensions again does not protect the process.

**Fix:** allow only the supported icon sizes before opening/allocating images, ideally serving prebuilt files. No oversized request was executed during this audit.

### 3. High — online verification omits session-window and terminal-state checks

**Source:** `web/checker.py:138–148`, `649–695`, `340–355`.

Online lookup checks owner, active term, and effective modality, but not session date or time. Actionability excludes only ABSENT and COMPLETED, so ACTIVE and CANCELLED also qualify. An on-duty checker can act on an owned future session, restore a cancelled online session, or verify an already active one. Verification resets `actual_start`; minute-based idempotency only suppresses a narrow repeat window.

**Fix:** define and reuse a server-side online action predicate covering date/time, duty, allowed source status, cancellation, and prior verification. Preserve the first authoritative start timestamp and use a guarded transactional transition.

### 4. High — offline observations are not tied to the capturing account

**Source:** `static/checker/offline_queue.js:22`, `120–127`, `144–174`.

One origin-wide IndexedDB queue stores records without an owner. It drains using the current session cookie. If checker A queues work and checker B signs in on the same device, A's observations are replayed as B; duty conflicts may instead flag and remove the observations. Server revalidation cannot recover an identity that was never recorded.

**Fix:** partition queues by authenticated account and bind replay to the recorded owner. Prevent account B from draining A's queue; make pending work visible during account changes.

### 5. High — room-change confirmation can produce two active occupants

**Source:** `scheduling/resolver.py:83–90`, `121–122`; `web/scan.py:187–197`.

The resolver returns WRONG_ROOM before evaluating destination occupancy. Its apply branch changes the session's room directly. An already ACTIVE class can move into another ACTIVE class's room without the occupied-room/handover path, leaving contradictory live occupancy.

**Fix:** resolve destination occupancy for room changes and serialize the destination-room decision and write. Require the intended handover/refusal behavior when occupied.

### 6. High — booking availability check and insert are not serialized

**Source:** `web/ifo.py:1170–1187`; `ops/models.py` Booking.

Booking creation checks `room_is_free`, then inserts in a separate autocommit operation. Two requests can both observe a free room and create overlapping bookings. There is no interval exclusion constraint or shared room-lock protocol to close that gap. The separate audit write can also fail after the booking persists.

**Fix:** lock the allocation resource, recheck availability, create the booking, and audit in one transaction. Use the same serialization protocol for all competing allocation writers. An `atomic()` wrapper alone does not serialize the empty-slot check.

### 7. High — manual schedules bypass operational conflict validation

**Source:** `web/ifo.py:2696–2727`; `scheduling/schedule_ops.py:109–125`.

The create path writes directly after basic field parsing without checking room availability, instructor overlap, or out-of-service state. It can create overlapping sessions or assign a closed room. Edits check room/time conflicts but do not validate a replacement faculty member's timetable.

**Fix:** introduce a shared schedule-writing service that validates all remaining occurrences, room service state, and faculty overlap while explicitly allowing legitimate merged sections.

### 8. High — schedule operations can rewrite a concurrently started class

**Source:** `scheduling/schedule_ops.py:130–140`, `167–175`.

Cancellation reads SCHEDULED IDs, then updates by ID without repeating the status predicate. Edit propagation similarly reads scheduled objects and later saves room/faculty/times unconditionally. A concurrent attendance transition after the read can be overwritten or have its live details rewritten. Locking only the schedule does not establish a shared lock protocol with attendance writers.

**Fix:** lock affected sessions using consistent ordering or use guarded updates with affected-row verification. Generate audits from the rows actually changed. These are source-derived concurrent interleavings, not a load-test reproduction.

### 9. Medium — web-push subscriptions allow arbitrary outbound destinations

**Source:** `web/push.py:48–60`; `ops/push.py:46–53`.

Subscription validation checks only an HTTPS string prefix and the presence of key values. With valid encryption keys, an authenticated user can persist a non-provider HTTPS destination; the scheduler sends a POST there when a push-worthy notification occurs. This creates a blind SSRF boundary when VAPID is configured and the target is reachable. No outbound-network exploit was attempted.

**Fix:** validate supported provider origins, endpoint shape, and destination safety; enforce outbound network restrictions and redirect safety. Bound subscription counts and validate key formats.

### 10. Medium — spreadsheet resource limits run after expensive parsing

**Source:** `scheduling/xlsx.py:45–48`, `193–212`; `web/ifo.py:1316`.

ZIP members are fully decompressed, XML trees built, and a dense grid allocated from unrestricted row/column coordinates before the web row limit is checked. A small sparse or compressed workbook can demand excessive memory. Access is restricted to IFO, but an accidental malformed institutional import can still take down a worker.

**Fix:** limit decompressed bytes, archive/member counts, XML complexity, coordinates, and grid cell count before allocation. Parse incrementally where practical.

### 11. Medium — closed-room state is bypassed by approval and confirmation

**Source:** `scheduling/services.py:574–576`; `ops/availability.py:202–229`; `web/scan.py:299–319`.

Dean approval chooses the original room if `room_is_free` returns true, although that function does not reject out-of-service rooms; only fallback enumeration does. Faculty resolution rejects closed rooms, but confirmation does not repeat that check after loading the room. A room closed after a token is issued can still be selected by its confirmation.

**Fix:** enforce room service eligibility at the allocation/application boundary and recheck it inside the transaction.

### 12. Medium — superseded modality reservations continue blocking rooms

**Source:** `ops/availability.py:88–119`, compared with `164–181`.

Reservation lookup treats every approved non-Online item as current. Recurring-schedule lookup, however, selects the latest approved shift. If an approved physical shift is followed by Online for the same dates, the old room reservation can remain blocking even though the session is released.

**Fix:** derive effective reservations from the latest applicable decision consistently, including cancellation/suspension semantics, rather than all historical approvals.

### 13. Medium — checker evidence and status changes can commit separately

**Source:** `web/checker.py:318–325`, `340–356`, `687–695`.

CheckerValidation and its audit are inserted before entering the transaction for online activation/merge propagation. A later failure can roll back activation while preserving evidence that it succeeded. The cache idempotency claim is made before application and is not released on failure, suppressing retry in the same bucket.

**Fix:** commit evidence, status, propagation, and consequential notifications as one unit. Use durable idempotency tied to the committed operation or clear failed claims safely.

### 14. Medium — normal faculty scan transitions have incomplete concurrency protection

**Source:** `web/scan.py:144–151`, `160–185`, `274`.

Normal transitions check an in-memory status before writing without locking the anchor or comparing the old status in the UPDATE. The resolve guard uses cache get/set rather than an atomic claim. Concurrent duplicate requests can duplicate audit events or replace timestamps; independent starts can both accept an empty room.

**Fix:** guard session transitions and room occupancy under a common transaction/lock protocol, with idempotency attached to successful application.

### 15. Medium — transient push failures are permanently marked handled

**Source:** `ops/push.py:55–62`, `80–99`.

Timeouts, network errors, 429, and 5xx return handled, after which the notification receives `pushed_at`. No later retry occurs for that notification. Pending rows older than the 15-minute window are also abandoned after a sufficiently long scheduler outage. In-app notifications remain available, so this is a push-delivery reliability issue rather than loss of the underlying notification record.

**Fix:** separate attempted/delivered/permanently-failed outcomes; use bounded retries/backoff and an explicit expiry/dead-letter policy.

### 16. Medium — offline capture retains stale session context

**Source:** `templates/checker/scan.html:98–108`; `web/views.py:211–215`.

Scanning a new room offline changes `pendingPayload` but leaves a prior online `pendingSessionId` intact. Replay can therefore reject an otherwise valid observation as a session mismatch. Separately, offline navigation always falls back to `/login`, so reopening the checker page offline cannot recover the capture interface.

**Fix:** reset session context when the scanned payload changes; design an account-isolated offline capture shell with clear stale-data indicators.

### 17. Medium — schedule field validation permits 500s and unusable schedules

**Source:** `web/ifo.py:2711–2721`, `2778`.

Enrollment is converted with unchecked `int(...)`; nonnumeric input raises ValueError, and negative values can fail database validation. Weekday checks only `.isdigit()`, accepting values outside 0–6 that never match materialization weekdays.

**Fix:** validate typed/ranged inputs through forms or a shared input schema and return field-level errors before ORM writes.

### 18. Medium — deployment commands do not load the documented service environment

**Source:** `deploy/deploy.sh:4–16`; `deploy/README.md` installation steps; systemd units' `EnvironmentFile` directives.

The runbook stores production variables in `/etc/fluxtrack/fluxtrack.env`, and services load that file. The deployment script does not load it before running checks, migrations, and collectstatic. Under the documented plain `sudo deploy/deploy.sh` invocation, absent a separately exported environment/root `.env`, management commands use development defaults or fail to connect instead of the service's production configuration.

**Fix:** execute deployment commands with the same validated environment as the services and fail immediately unless production mode is active. Verify this on a clean host; no Linux deployment was executed here.

## Maintainability and verification observations

- The pure-core/service/view pattern is a strong foundation but is applied unevenly. Booking and schedule creation still perform domain writes directly in a very large `web/ifo.py`, while checker and scan apply logic remain coupled to HTTP modules. Consolidating those seams would reduce alternate-path policy gaps.
- Broad regression coverage includes role scoping, reports, lifecycle, imports, merge behavior, room service state, and replay. Some tests assert source strings or mocked outcomes; these are useful wiring guards, but they cannot establish real database concurrency, browser account isolation, or a working deployed service.
- No tracked `.github` CI workflow was found. A SQL Server CI job and targeted browser checks would make the documented verification baseline repeatable.
- Several requirements are lower-bound-only rather than locked. The README's claim that packages are pinned overstates reproducibility; production deployment resolves dependencies during each release.
- `/healthz/` is intentionally process liveness only. It does not prove database readiness, scheduler progress, valid Entra configuration, or working report storage; monitoring must treat those separately.
- Some comments/documentation lag the implemented system, for example the User model's claim that Entra cutover is not yet implemented. Historical audit and planning documents were treated as context, not fresh evidence.

## Recommended order of work

1. Close browser account-isolation and public icon allocation issues.
2. Guard online/check-in state transitions and wrong-room occupancy; centralize transactional evidence/idempotency.
3. Establish one room-allocation protocol for bookings, schedules, confirmations, and approvals.
4. Harden push destinations, spreadsheet parsing, input validation, and retry behavior.
5. Fix deployment environment loading; add repeatable SQL Server and browser regression checks.
6. Complete institutional Entra UAT, backup/restore rehearsal, and role-by-role production smoke tests before official attendance use.
